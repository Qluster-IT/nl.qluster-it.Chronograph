## App-specific instructions
- Follow `C:\Users\Qlustrator\.copilot\instructions\homey-colors.md` as the source of truth for shared palette IDs/values, Homey token/fallback pairs, and preview parity. Preserve Chronograph-specific colors and saved theme appearance.
- In Dutch, translate the Chronograph type "transition" as "transitie" (plural "transities"), not "overgang" or "overgangen".
- The widget should let a user select a timer, stopwatch, or transition and provide controls to pause, resume, and stop the selected chronograph.
- Missing widget styling capabilities should become designer options, not changes to shared defaults. Match new design requests through preset-specific settings; preserve the appearance of other built-in designs and existing dashboard configurations.
- The current Chronograph TWF version is v1: `[twf:Chronograph:Chronographs:DESIGN|THEME|DESIGN,THEME:"<payload>":/twf]` with a Brotli-compressed, key-shortened `{v:1,d?,t?}` body. Timer, stopwatch, transition and multi-widget variants share the Chronographs family. Reject unreleased v2, family-less headers and prototype encodings. Version changes are independent of other apps and stored widget collections.
- Widget bundles preserve pre-minified Angular and Font Awesome assets, including their licences, verbatim. Minify only app-owned code and fail the CSS build on errors or warnings rather than dropping unsupported selectors.
- Keep widget and preview typography in `assets/css/chronograph-typography.css`, loaded by settings and the widget bundle. Opt app-styled widget controls out of Homey's form styling with `hy-nostyle`; preserve design sizing and explicit theme overrides.
- Interactive designer, single/multi and catalog preview names use the singular type label in the Homey user's language: Stopwatch, Timer or Transition (Dutch: Transitie). Generated template images use the English names and English type headings regardless of the user's language. Reuse the `widget_type_*` translations and shared preview-name helper; do not use generic Chronograph or plural type labels for sample names.
- Generated template images paint the space behind/outside widgets with the corresponding real dashboard backdrop from `homey-colors.md`, independently of editor mode and the selected widget theme. Keep widget surfaces, borders, rounded corners and transparent gaps separate so the frame remains visible; follow `homey-images.md` for the distinction from transparent App Store/picker artwork.
- Compare custom design/theme previews with native widget captures at the same CSS viewport and size, including element line heights, square/round controls, foreground/border overrides and progress track/fill styling. Preserve saved custom configurations; sample names, durations and progress amounts are illustrative rather than live instance data.
- Keep configured identities separate from runtime instances: collect only literal saved Flow names and explicit picker selections, excluding wildcards. Do not execute BLL or resolve Homey tags/tokens while rebuilding configuration. Syntax checks here classify identities; runtime decoding still calls BLL directly without delimiter pre-checks.
- Runtime starts must not add configured names. Keep resolved names and start metadata on the instance and its restart snapshot; save reusable defaults only for names that are independently configured. Changing a coding/tag/token value affects future starts, never an existing instance's identity.
- Announce API readiness through `/api-ready` and the `api-ready` realtime event only after initial Flow registration, configured-name collection and snapshot restoration succeed. SDK app availability is necessary but does not mean this initialization has finished.

## Homey testing
- For a requested deployment to HP2023, check the saved CLI selection offline first; use the existing `homey select -n HP2023` command from `.vscode/launch.json` only if the target differs or is absent. Follow the general persistent-install and readiness checks. Resolve the current address at connection time rather than copying the launch configuration's debugger address.
- Keep reusable test Flows in the top-level `Chronograph` folder and test devices in the `Chronograph` zone. Reuse them on subsequent test runs and verify their behavior.
- Before pairing Chronograph test devices, create and save enabled Flows containing the named timer, stopwatch, and transition. The pairing list reads the app's configured chronograph registry for the selected type, rather than raw start, resume, or trigger card arguments.
- On Homey, test configured/runtime separation with changing BLL values, direct Homey tags/tokens, and time-dependent coding such as `{[ now ]}`. Verify that only literal/picker identities enter the configured list, wildcard rules never become candidates, dynamic instances remain visible while running/paused under their original names, and stopping/completing them leaves no configured entries. Verify restart restoration without promoting runtime names into configuration.
- After installation or restart, verify `/api-ready` before using the app API; retry only expected startup errors with a bounded timeout. Run restart tests separately from active pairing sessions, which an app restart invalidates.
- Compare configured-name membership, not array order, when asserting that restart restoration leaves configuration unchanged.
- Inspect the real device-creation UI as part of these Homey tests: navigate to the existing `Chronograph` zone first, open pairing for each type, and verify that candidates match that type's stable configured names. Reject raw expressions/tokens, wildcard patterns, and runtime-only resolved names; check for duplicates and verify that created devices land in the same zone with their expected names and controls. Record the UI result separately from API/unit-test results; do not claim it passed without inspecting the browser.
- The reusable fixture chronographs are `Chronograph test timer`, `Chronograph test stopwatch`, and `Chronograph test transition`. Each type has three Advanced Flows: `Test - <Type> - Lifecycle`, `Test - <Type> - Wildcards and expressions`, and `Test - <Type> - BLL coding and picker precedence`. Do not recreate the former individual basic test Flows.
- Run each Lifecycle Advanced Flow to verify start, pause, resume, stop, running conditions, duration-return tokens, advancing duration, and frozen duration while paused. Timers and transitions also complete automatically after two seconds.
- Group related cases into manageable Advanced Flows. Include wildcard actions, conditions, and triggers with multiple matching chronographs, nonmatching controls, and type isolation; do not test only exact names.
- Saved Flow tests must cover picker-only (`namedd`), typed-name-only (`name`), and conflicting picker/typed-name inputs. Use real autocomplete selections and verify that the picker takes precedence, across relevant actions, conditions, and triggers.
- Include math.js duration expressions in the supported start, resume, and adjust cards. Verify the evaluated durations and resulting state, along with duration-return tokens, comparisons, and timer/transition milestones; do not treat successful card execution alone as proof of the expected result.
- Include actual Better Logic Library integration tests for variable-driven chronograph names, durations and wildcard matches, combining BLL output with supported math.js expressions. Change BLL values between runs, verify the resolved names and durations, and confirm that a selected picker name overrides the typed BLL name without evaluating the ignored name.
- The BLL scenarios reuse variables `Chronograph test <type> BLL name` and `Chronograph test <type> BLL seconds`, and chronographs ending in `BLL A` and `BLL B`. They change the variables within a run, assert 13- and 17-second targets for timers/transitions, adjust both wildcard matches by two seconds, preserve the nonmatching control, and test picker precedence over the changed BLL name. Keep references to `BLL A`/`BLL B` coded or token-based, not literal, so the test itself does not configure those identities. Also exercise `Chronograph test <type> timestamp {[ now ]}` through pause/resume and completion (or stop for stopwatches). BLL expression cards perform assertions in the saved Flows; do not replace them with unverified successful actions.
- All nine Advanced Flows report scenario START/PASS/FAIL and measured durations to Simple (Sys) Log under the `Chronograph` group. The result variable records the current section for failure diagnostics. Preserve the error/false branches when updating these graphs.
- Lifecycle scenarios use real autocomplete selections for actions, conditions, and event triggers, including conflicting typed BLL names. They also compare remaining timer duration or elapsed stopwatch/transition duration. Wildcard scenarios retain typed-name coverage.
- Event-observer Flows write `started`, `paused`, `stopped`, and, for timers and transitions, `finished` to the corresponding text variable `Chronograph test <type> event`. Verify these values to test actual trigger execution, rather than only card registration.
- The Wildcards and expressions Advanced Flows use `Chronograph test <type> group A`, `group B`, and an `other` control, plus a same-named chronograph of a different type. Verify that wildcard pause/resume/adjust/stop affects both matches but neither control, and that wildcard started triggers report the expected names.
- Expression cases include `max(10, 4 ^ 2)`, `floor(16.9)`, `ceil(1.2)`, and `round(15 / 2)` on supported cards. Verify actual target/elapsed durations and the saved numeric `Chronograph test <type> duration` value. Each Advanced Flow must finish with its `Chronograph test <type> result` text variable set to `PASS`; the fixtures must not remain active afterward.
- Pair the three fixture devices into the `Chronograph` zone and verify their duration, active state, pause/resume, and start/stop behavior against the same chronographs on subsequent test runs.

## Fast local widget validation

- After changing bundled widget JS/CSS, run `npm run build:widget-assets` before tests or deployment. Keep generated bundles consistent with their sources; no dependency installation is needed unless dependencies changed or a required tool is missing.
- Tests run through the nested development package, so Mocha arguments need both forwarding separators. For widget/template/icon/localization changes, use `npm test -- -- --grep 'Widget|Multiple Chronographs|Homey Compose locales' --reporter dot`; narrow the expression for a smaller change. Reuse passing results while the tested sources remain unchanged rather than rerunning the same suite before each deployment. Run `git -c core.safecrlf=false --no-pager diff --check` for whitespace validation.
- Use `node tools\development\settings-preview.js` for local designer checks without Homey access. The default URL is `http://127.0.0.1:4178/settings/index.html?lang=en`; set `CHRONOGRAPH_PREVIEW_PORT` when that port is in use. The helper uses real template encode/decode and local icon assets, but simulated Homey settings/state: do not report these checks as live-Homey tests.
- Preserve and restore any preview localStorage values changed by browser fixtures. For actual widget rendering, use the rebuilt bundle and local assets, checking explicit icon overrides as well as design defaults across single/multi widgets.
- The integrated browser may keep pages hidden, suspending `requestAnimationFrame` and pointer-stability waits. For nonvisual asynchronous checks, use interval polling (for example Playwright `polling: 100`); dispatch a DOM click only when testing handler behavior, not as evidence of pointer usability. Report screenshots/layout checks separately.
- For automatic forum-post copy, call `clipboard.write()` on the Create TWF click with promise-backed `ClipboardItem` data. Encoding and image rendering can outlast browser user activation. The Async Clipboard API needs a secure context; retain the click-triggered copy fallback for local HTTP Homey settings.
- For task-only preview servers, verify the HTTP endpoint is responsive, then navigate temporary browser fixtures to `about:blank` and stop only the helper process started for that task. Do not leave polling widgets or preview servers running after validation.
